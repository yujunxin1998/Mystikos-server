# Mystikos Server 设计文档

Mystikos 是一个陪玩公会平台：老板（付费用户）在站内预约陪玩服务、参与排行榜与等级体系、和陪玩建立亲密度关系、赠送礼物，并可购买公会周边商品。后端服务于 Nuxt 4 + Vue3 + TypeScript 前端（C 端）。

## 当前状态

- 技术栈已确定：JDK 17、Spring Boot 3.x、MyBatis-Plus、Spring Security OAuth2、PostgreSQL；前端 Nuxt 4 + Vue3 + TS。
- 领域模型与包结构已完成设计（见上方文档）。
- **Maven 多模块脚手架已搭建完成，21 个模块全部编译通过**（`mvn compile`，JDK 17）：
  - `mystikos-common` / `mystikos-common-web`：统一响应封装、全局异常处理
  - `mystikos-common-event`：领域事件基类 + 发布端口（Spring ApplicationEventPublisher 实现）
  - `mystikos-common-security`：当前用户上下文工具类 + **自签发 JWT 的签发/校验/过滤器**（`JwtTokenService`/`JwtAuthenticationFilter`/`SecurityConfig`）。鉴权模型已确定：本地账号和第三方登录成功后都由我们自己签发 JWT，不接外部 OAuth2 Authorization Server 的 issuer-uri/JWKS。
  - `mystikos-common-cache`：**Redis 接入**，`RedisConfig` 提供 key=String/value=JSON 序列化的 `RedisTemplate`；新增 `RateLimiter`（固定窗口限流，INCR+EXPIRE）供业务模块直接注入用。
  - `mystikos-common-storage`：**MinIO 对象存储接入**，`ObjectStorageService` 端口 + `MinioObjectStorageService` 实现，配套通用接口 `/api/v1/files`（上传/预签名下载链接/删除，需登录）。
  - `mystikos-common-region`：**行政区划参考数据**（国家 + 一级行政区两层树，`common_region` 表，主键直接用 ISO 3166-1/3166-2 编码而不是雪花ID），`GET /api/v1/regions/tree` 只读公开接口，供前端渲染树状选择器；定位和 `mystikos-common-storage` 一样是纯技术能力，不是限界上下文，任何业务模块要用地区数据直接依赖它即可，见下方 `mystikos-identity` 扩展说明。
  - `mystikos-booking`：**五层 DDD 结构的完整打样实现**——聚合根状态机、仓储接口/实现、MyBatis-Plus 持久化、PostgreSQL 迁移脚本（含防重叠的 `EXCLUDE USING gist` 约束）、REST 端点（`/api/v1/bookings`）。已在本地 PostgreSQL 跑通（迁移版本 `V1`）。
  - `mystikos-identity`：**S1 账号与认证 + S2 用户资料（老板侧）已实现**——手机号/邮箱二选一注册、密码或验证码登录、自签发 JWT + 可吊销 Refresh Token、**Discord 第三方登录已接入**（`/api/v1/auth/oauth/discord/login`，其他 Provider 仍占位）；固定 6 角色枚举 `Role`（游客/会员用户/陪玩/客服/考核官/管理员）+ RBAC 权限表；会员等级挂点（`MembershipTier` 接口在 `mystikos-common`，梯度故意留空）；老板资料已细化——昵称/匿名上榜、性别（`gender`，自报三态）、头像（`avatarUrl`）、生日（`birthDate`，仅展示不作实名认证依据）、个性签名（`bio`）、地区（`regionCode`，引用 `mystikos-common-region` 的 `common_region.code`）、标签（`tagIds`，游戏类型等，后台配置目录见下）都已实现（`ProfileController`）。**标签目录**（`TagDefinition`）是新的一小块管理态能力：`category` 是自由字符串不预置枚举，`GET /api/v1/tags` 公开只读、`POST/PUT /api/v1/tags/*` 是运营态写操作（权限校验粒度同 `UserController` 现有其他管理态接口，仅要求登录，没有角色级 `@PreAuthorize`，是这个代码库当前一致的做法）。
  - `mystikos-gifting` / `mystikos-relationship` / `mystikos-leaderboard` / `mystikos-membership` / `mystikos-commerce`：**S3/S4/S5 已实现**，见下方专门一条说明。
  - `provider-catalog` / `payment` / `review` / `trust-safety` / `notification`：Maven 模块骨架已建，内部五层结构留空待实现，实现时参照 `mystikos-booking` / `mystikos-identity`
  - `mystikos-app`：启动壳，聚合全部模块的单体可执行 jar，本地开发默认接 Flyway（指向仓库根目录的 `deploy/sql`，见下；线上/测试环境打包不带 Flyway，见下方专门一条）、Knife4j 接口文档（本地 `http://localhost:8080/doc.html`）、JWT 密钥占位配置
- **所有 SQL 迁移脚本集中在 `deploy/sql/`**（`V1`-`V16`），不再按模块拆在各自 `src/main/resources` 下；跨模块共用同一个 Flyway 版本序列，新增迁移前看一眼当前最大版本号接着编。`V4` 是内置超级管理员种子数据：`administrator@mystikos.local` / `Mystikos@123`（邮箱渠道登录，因为登录模型没有裸用户名概念），密码哈希是用项目实际依赖的 `spring-security-crypto` 生成并验证过的，不是编的字符串；上线前必须改密码。`V5` 把 `Role` 枚举镜像成 `identity_role` 表并预置 6 个角色，给 `identity_user_role`/`identity_role_permission` 补外键完整性——枚举仍是行为/展示名的权威来源，表只用于外键约束，新增角色要两边同步改。`V6` 删掉了 `identity_verification_code` 表——验证码改存 Redis 了，见下一条。`V7` 给 V1-V6 建的所有表/列补了 `COMMENT ON TABLE`/`COMMENT ON COLUMN`（之前的迁移都没写），**从 V7 起新表必须同步写 COMMENT，不再事后补**。`V8`-`V12` 分别是 Gifting/Relationship/Leaderboard/Membership/Commerce 五个新上下文的建表脚本，见下方 S3/S4/S5 说明。`V13` 给 `identity_user` 补性别/头像/生日/个性签名/地区字段；`V14` 建标签目录表；`V15` 建 `mystikos-common-region` 的行政区划参考表；`V16` 把 `identity_user.region` 重命名成 `region_code`——**`V13` 已经在本地开发库跑过一次之后才决定改字段名**，Flyway 不允许悄悄改写已应用迁移的内容（会触发 checksum 校验失败），只能像这样另开一个新版本号做重命名，这是本次踩的一个小坑，记一下：**迁移文件一旦有实例真正跑过，就不能再回头编辑，只能往前追加新迁移**。
- **线上/测试环境部署不用 Flyway 增量迁移，改用一次性的 `deploy/init.sql`**：本地开发继续用上面的 Flyway 版本化迁移（改一次表加一个 `V` 文件，方便），但 `mystikos-app` 现在有两个 Maven profile——默认的 `local`（`mvn package`，带 `flyway-core`，启动自动跑 `deploy/sql/V1..N`）和显式指定的 `deploy`（`mvn package -Pdeploy`，classpath 里没有 `flyway-core`，`FlywayAutoConfiguration` 直接不激活，启动完全不碰迁移）。`deploy/init.sql` 是把本地全部迁移跑完之后的最终结构（表/约束/索引/`COMMENT`）+ 种子数据（管理员账号/角色/礼物目录/标签目录/商城商品库存/行政区划）用 `pg_dump` 导出拼成的完整快照，已经在一个全新数据库上验证过能一次跑通（`psql -f deploy/init.sql`）。线上/测试环境部署前手动执行这一个文件初始化数据库，**之后这套环境的表结构变更不再走脚本化迁移，由人工手动 `ALTER`**——这是显式的取舍：换取"线上环境的 schema 变更节奏完全由人控制，不会被一次 `mvn package` 自动改动"，代价是 `deploy/init.sql` 需要在本地迁移变多之后手动重新生成（`init.sql` 文件顶部注释里写了怎么重新导出）。
- **接口文档用 Knife4j**：运行时只在 `mystikos-app` 引入，业务模块只依赖 `swagger-annotations-jakarta` 注解类；持久化实体（PO）和请求 DTO 统一按"`@Schema` 描述 + 显式 `@TableField` + javadoc + `Serializable`/`@Serial serialVersionUID`"的风格写。已加**全局 Bearer 认证声明**（`OpenApiConfig`），Knife4j 界面右上角"Authorize"填一次 token 后所有调试请求自动带上；已按**限界上下文**分组（`SpringDocGroupConfig`，对齐 [领域模型](architecture/domain-model.md) 的 Bounded Context 划分，不是按 URL 前缀/PRD 功能编号）：`Identity & Access · 身份与访问`（合并了 S1 账号认证/S2 用户资料/运营态用户与角色管理三块 Controller）、`Booking · 预约撮合`、`Gifting · 礼物打赏`、`Relationship · 亲密度`、`Leaderboard & Stats · 排行榜`、`Membership · 会员成长`、`Commerce · 商城`、`通用能力 · 文件存储与行政区划`（不是业务上下文，单列，`/api/v1/files/**` + `/api/v1/regions/**`）；新模块有真实接口后照此补分组。
- **所有 Controller 统一走 `/api/v1/*` 前缀**（PRD 要求，之前 Booking/Identity 都漏了，已补齐）。新增 `GET /api/v1/roles` 查角色列表（读枚举不查库）。
- `GlobalExceptionHandler` 加了 `NoResourceFoundException` 专门处理（比如浏览器打开 `/doc.html` 自动带的 `favicon.ico` 请求），返回正常 404，不再当系统异常打 ERROR 日志刷屏。
- **依赖服务（Postgres/Redis/MinIO）的本地 Docker 起法见 `deploy/docker/README.md`**（含镜像版本对照表和 `docker run` 命令；后续配置稳定后会合并成 `docker-compose.yaml`）。Redis 选了 `redis:7.2-alpine`（最后一个 BSD 协议版本，规避 7.4+ 的 RSAL/SSPL、8.0+ 的 AGPL 协议风险）；MinIO 选了官方停更前最后一版 `RELEASE.2025-09-07T16-13-09Z-cpuv1`（MinIO 2025 年 10 月起不再发布免费镜像，生产上线前需重新评估镜像来源）。
- **验证码存储从 Postgres 迁到了 Redis，登录/验证码接口也接上了限流**：`mystikos-identity` 的 `RedisVerificationCodeRepositoryImpl` 用 key 的 TTL 存验证码（不用清理任务，过期自动消失）；`AuthApplicationService` 用 `mystikos-common-cache` 新增的 `RateLimiter`（固定窗口限流）挡住撞库/轰炸——`/auth/verification-codes` 同一 channel+identifier 60 秒只能发一次（不分 purpose，避免绕过），`/auth/login` 同一 channel+identifier 15 分钟最多 10 次尝试，超限抛 `VERIFICATION_CODE_RATE_LIMITED`(2014)/`LOGIN_RATE_LIMITED`(2015)。
- 已验证端到端跑通：本地起了 Postgres（原生服务）+ Redis/MinIO（Docker 容器，见 `deploy/docker/`），`mystikos-app` 打包成可执行 jar 后实测登录、`/api/v1/auth/me`、文件上传/预签名下载/删除全部走通。**踩过一个坑**：`mystikos-app/pom.xml` 的 `spring-boot-maven-plugin` 之前没绑定 `repackage` 到 `package` 阶段（这个自动绑定只有用 `spring-boot-starter-parent` 做父 POM 才有，本项目父 POM 是自己的），导致 `mvn package` 产出的是不能 `java -jar` 直接跑的瘦 jar，已修复。
- **邮箱验证码 / 短信验证码 / Discord 登录三件事都接了骨架**（目标市场先欧洲、后美洲澳洲，不是国内用户为主，选型和文案都按这个前提定的）：
  - **邮件**：走通用 SMTP（`spring-boot-starter-mail`），不绑定具体厂商——`mystikos.mail.enabled=true` 时用 `SmtpEmailSender` 真实发信（配 `spring.mail.host/port/username/password`），默认 `false` 时用 `LoggingEmailSender` 只打日志，本地开发不用配任何账号就能跑。
  - **短信**：厂商还没定（候选 Twilio 这类全球覆盖的，不是国内阿里云/腾讯云那一挂），`SmsSender` 接口先立好，`UnconfiguredSmsSender` 打日志占位，选定厂商后加一个真实实现替换掉就行，`AuthApplicationService` 不用改。
  - **Discord 登录**：`OAuthProviderClient` 接口 + `DiscordOAuthClient` 真实实现（标准 authorization_code 流程，拿 code 换 token 再换用户信息）；`client-id` 没配置时这个 Bean 不注册，走"该第三方登录方式暂未开放"而不是拿空凭证瞎调 Discord API。首次登录本地找不到绑定会自动注册新用户（`User.registerWithOAuth`，默认给 MEMBER 角色），已绑定就直接登录。**需要你在 `application.yml`（或环境变量 `DISCORD_CLIENT_ID`/`DISCORD_CLIENT_SECRET`/`DISCORD_REDIRECT_URI`）里填真实凭证才能跑通**，redirect-uri 要和 Discord Developer Portal 应用配置、前端发起授权时用的 URI 三处完全一致。
  - `VerificationCodeSender` 现在按 channel 路由到 `EmailSender`/`SmsSender`（`ChannelRoutingVerificationCodeSender`），验证码/通知文案用的是英文（呼应目标市场）。
- **S3（排行榜与等级）/ S4（亲密度与礼物成就）/ S5（商城与订单）已实现**，对应 5 个限界上下文（`mystikos-gifting`/`mystikos-relationship`/`mystikos-leaderboard`/`mystikos-membership`/`mystikos-commerce`），迁移 `V8`-`V12`：
  - **依赖顺序**：Gifting 是事件源头（`GiftSentEvent`），Relationship/Leaderboard/Membership 都订阅它做累加，三个模块因此都在 pom.xml 里加了 `mystikos-gifting` 依赖（方向是"消费方依赖发布方"，Gifting 不反向依赖它们，不会循环）。事件监听器统一用 `@TransactionalEventListener(phase = AFTER_COMMIT)`，不是普通 `@EventListener`——赠礼这笔流水必须先真正提交，下游累加才跟着做，这是本次给项目立的新precedent，后续新增跨上下文事件消费都应该照这个写。
  - **Gifting（礼物打赏）**：`GiftCatalogItem`（目录）+ `GiftTransaction`（流水），解锁规则支持 `CUMULATIVE_COUNT`/`CUMULATIVE_SPEND`（自己的流水表就能算，已实现评估）；`CONSECUTIVE_DAYS`/`LEADERBOARD_RANK`/`INTIMACY_STAGE` 只存配置不评估——真做的话需要 Gifting 反向查询 Leaderboard/Relationship，会和"这两个上下文订阅 Gifting 事件"的方向形成循环模块依赖，Maven 编不过，故意留空。`POST /api/v1/gifts/send`（登录态，赠送方是当前用户）、`GET /api/v1/gifts/catalog`。种子数据是原型里的 6 款礼物（鲜花/蜡烛/信笺/耳环/皇冠/星辰吊坠），价格和解锁阈值都是占位值。
  - **Relationship（亲密度）**：`IntimacyRecord`（patronId+companionId 唯一，stage 0-4），阶段门槛（`IntimacyStagePolicy`）是占位值，业务确认后直接改常量。目前只由 Gifting 的赠礼金额累加驱动——Booking 完成度那一路接不上，因为 `BookingApplicationService` 至今只实现了 `createBooking`，没有任何用例真正推进到 `COMPLETED` 并发事件。`GET /api/v1/relationships/{patronId}/{companionId}`，无记录时返回 stage 0，不报 404。
  - **Leaderboard（排行榜）**：陪玩魅力榜/老板守护榜，纯读侧投影，**排名实时计算**（每次查询时按累计值 `ORDER BY ... LIMIT`），不落周更快照——UI 原型文案写的是"每周一更新"，但先做实时版本更简单，要改成真正冻结的周榜需要另加 `@Scheduled` 定时任务。`GET /api/v1/leaderboard/companions`、`GET /api/v1/leaderboard/patrons`（`limit` 参数，默认 50，上限 100）。
  - **Membership（会员成长）**：`MembershipAccount`（1:1 挂老板用户），等级梯度 `DefaultMembershipTier`（LV1-LV5，累计消费门槛）是占位值——这是 `mystikos-common` 的 `MembershipTier` 接口第一次有真实实现。**消费累计的触发源是临时顶替方案**：按领域事件图，Membership 该订阅 `mystikos-payment` 的 `PaymentCaptured`，但 Payment 上下文还没建（S6，不在这次范围内），先订阅 Gifting 的 `GiftSentEvent` 顶替，代码里有醒目的 `TODO(payment-integration)` 注释标记这块以后要换。等级升级后通过 `MembershipTierUpgradedEvent` 同步投影到 `mystikos-identity` 的 `User.membershipTierLevel/Code`（新增 `MembershipTierUpgradedEventListener`，Identity 因此加了 `mystikos-membership` 依赖）——这两个字段本来就是"挂点占位"设计，现在终于有真实数据源。`GET /api/v1/memberships/{patronId}`。
  - **Commerce（商城）**：`Product`（目录）+ `CartItem`/`WishlistItem`（按 patronId+productId 唯一，不建"购物车"聚合包一层）+ `MerchandiseOrder`+`OrderLineItem`（订单行快照）+ `InventoryStock`（下单预占、取消释放，不做超卖）。**故意没做**：`Product.recommendedBy`/`eligibilityRule`（陪玩确认授权的推荐关联工作流）——讨论后决定这次先不做，见 prd-alignment.md 的缺口清单，后续单独排期。订单和 `booking_order` 一样卡在 `DRAFT`，没接支付（`requestPayment`/`markPaid` 等状态机方法留在聚合上但没接用例）；下单会预占库存、清空购物车，取消订单会释放库存。`GET /api/v1/products`、`GET/POST/DELETE /api/v1/cart`、`GET/POST/DELETE /api/v1/wishlist`、`POST /api/v1/orders`、`GET /api/v1/orders/{id}`、`POST /api/v1/orders/{id}/cancel`。
  - **踩过一个坑**：Relationship/Leaderboard/Membership 三个模块一开始都建了一个同名类 `GiftSentEventListener`（各自的 `infrastructure.acl` 包下），单模块编译各自都过，但 Spring 按简单类名生成 Bean 名，三个类在同一个应用上下文里全部撞名成 `giftSentEventListener`，**启动直接报 `ConflictingBeanDefinitionException`**——这种问题编译期发现不了，只有整个 `mystikos-app` 真正启动扫描全部 Bean 才会暴露。已重命名为 `RelationshipGiftSentEventListener`/`LeaderboardGiftSentEventListener`/`MembershipGiftSentEventListener`，以后同名类跨模块碰撞的坑记一下。
